# PLAN — one HTTP tool, and what it replaces

**Status:** plan, not started. Written 2026-11-06.

**The decision this implements.** The operator: *"do we even need gh or just curl is enough? not just
for github api but for any api… I want to provide the minimal control interface (a set of essential
commands) for agent to push and pull from his project's repo, setup the workflows and upload their
artifacts into the app (basically I want agent to use workflows as his stdin and stdout)… and I may be
blind to the work details of what is really needed for that, but I don't want to overbuild it."*

So: **one general-purpose HTTP tool, a vault-backed auth handle, and the deletion of the tools it
subsumes.** Nothing typed per-service.

---

## 0. What already exists, measured

| Thing | Where | What it means for this plan |
|---|---|---|
| `Fetcher.bytes(url, limit)` | `Fetcher.kt:29` | **GET only**, manual redirect following with the address check **on every hop**, size counted *while reading* and stopped at the cap. This is the whole transport; `http` is a method/headers/body wrapper over it. |
| `Fetched.LIMIT_BYTES` | `Fetcher.kt:196` | 100 MB. **A memory cap, not a context cap** — see §4. |
| `Fetched.nameFor(url)` | `Fetcher.kt:206` | The URL→filename rule, already written and tested. `http` reuses it. |
| `Fetched.DIR` | `Fetcher.kt:179` | `agent/fetched`. `http` gets its own. |
| `Addresses.problem(url, privateAllowed)` | `browser/Browser.kt:175` | The SSRF guard, applied at three sites today. `http` becomes the fourth. |
| `Credentials.secret(name)` / `setSecret` | `CredentialStore.kt:78` | The vault. Per-account, encrypted with the keystore key, unreadable while locked, scrubbed from messages. |
| `McpServer.authorization(credentials)` | `Mcp.kt:54` | The existing precedent: an article names a secret, the store resolves it, **the value never reaches the model.** |
| `AgentTools.forConversation` | `AgentTools.kt:4361` | A result over the token budget is **filed whole** and answered with a path. Already the rule for every tool. |
| `AgentTools.KEYS` | `AgentTools.kt:404` | The argument table — the single place a tool's keys are declared, and `unknownIn` refuses keys not listed. |
| `AgentTools.specs()` | `AgentTools.kt:537` | The descriptions the model reads. One `spec(...)` per tool. |
| `when (call.tool)` | `AgentTools.kt:1029` | The dispatch table. |

**Nothing here needs new infrastructure.** The transport, the guard, the vault, the filing rule and the
naming rule all exist. `http` is a composition, and that is why it is worth doing.

## 1. What must be implemented

### 1.1 `Fetcher.request` — the transport

`Fetcher` gains one method beside `bytes`:

```kotlin
fun request(
    url: String,
    method: String,                 // GET, POST, PUT, PATCH, DELETE, HEAD
    headers: Map<String, String>,   // already resolved — never contains a vault value
    body: ByteArray?,               // null for no body
    limitBytes: Long,
): Result<Answer>

data class Answer(val status: Int, val headers: Map<String, String>, val bytes: ByteArray)
```

**What it must keep from `bytes`, and each is a measured decision rather than a style:**

1. **The address check on every hop.** `bytes` follows redirects by hand precisely so `Addresses.problem`
   can run again on each `Location`. A `request` that used `HttpURLConnection`'s automatic following
   would check the URL the agent typed and then walk to `127.0.0.1`.
2. **The count-while-reading cap.** `Content-Length` is a claim; a server that omits it and keeps
   writing is the case a cap exists for.
3. **The status, separately from the body.** A 404's body is the diagnostic and the status is the fact.
   `bytes` throws the status away; `request` must not, because an API's whole vocabulary is statuses.
4. **`Accept: */*` and a `User-Agent`** — GitHub's API rejects a request without a user agent.

**What is new:** the method, the headers, the body, and the status.

**What it must NOT do:** follow a redirect for a non-GET. A `POST` that is redirected to a `GET`
silently loses its body, and GitHub's API does this on repository renames. A 3xx on a non-GET is
returned to the caller as a status, not followed.

### 1.2 The `http` tool

```kotlin
"http" to setOf("method", "url", "headers", "body", "auth")
```

| Key | Meaning |
|---|---|
| `method` | `GET` when absent. One of the six. Anything else is refused by name. |
| `url` | The address. Through `Addresses.problem` before anything is opened. |
| `headers` | A JSON object of header names to values. **`authorization`, `cookie`, `proxy-authorization` and `x-api-key` are refused here** — see §1.3. |
| `body` | A string. Sent as UTF-8 with the caller's `content-type`, defaulting to `application/json`. |
| `auth` | **A name in the vault.** The app resolves it to an `Authorization` header. Never a value. |

**The answer** follows the app's established shape — a path, a size, a status:

```
0
POST https://api.github.com/repos/o/r/git/refs → 201 Created (412 bytes)
written to agent/http/refs-a1b2c3.json

It holds: {"ref":"refs/heads/x","object":{"sha":"…"}}
```

**Where the bytes go, and why it is not a choice:**

- **A body that is text and small** (under a few KB) is answered inline *and* filed, because an agent
  reading a 200-byte JSON to decide its next call should not have to make a second call to read it.
- **Anything else is filed only**, and the answer names the path — the same rule as `fetch`, `runs` and
  `artifact`. A PNG in the conversation costs the window to say nothing.
- **The folder is `agent/http/`**, and the name is `Fetched.nameFor(url)` with a short hash of the
  method and body appended, so that two POSTs to the same URL do not overwrite each other. **The agent
  does not name the file**; the answer tells it where the file is.

### 1.3 The vault handle

This is the part that makes the tool safe, and it is three rules:

1. **`auth: "name"` resolves through `Credentials.secret(name)`.** Missing secret → a refusal that
   names the article or setting that would create it, not "401".
2. **An agent-written header may not be `authorization`/`cookie`/`proxy-authorization`/`x-api-key`.**
   If it could, the vault would be decorative — the agent would just type the token. This is checked
   before the request is made, and the refusal says which header and why.
3. **The resolved value is never echoed.** Not in the answer, not in a trace, not in the request log,
   not in a `background` result. `Secrets` already scrubs known values from messages; the vault value
   must be registered with it for the duration of the call, or the answer must be built so it cannot
   contain it.

**Rule 3 is the one that needs a test that fails if it breaks**, because a token in a log is
unrecoverable and invisible.

### 1.4 The description the model reads

One `spec("http", …)` in `AgentTools.specs()`, and it has to teach four things a model will otherwise
get wrong:

- **`auth` is a name, not a value.** The single most important sentence in the description.
- **A status is the answer.** `200` is not "it worked" for every API; `201`/`204`/`404` all mean
  something and the tool reports the number.
- **The body is filed, and the answer says where.** With the range/grep idiom it already knows from
  `read`.
- **When not to use it.** If a workflow can do the job, the workflow is cheaper to repeat and leaves a
  record; `http` is for a question, not for work.

### 1.5 Tests — each with what fails if it is removed

| # | Test | Fails if removed |
|---|---|---|
| 1 | A GET returns the status and files the body | the status is lost and every API answer reads as success |
| 2 | A POST sends its body and its `content-type` | the body arrives empty |
| 3 | `auth` puts `Authorization` on the request | the vault is decorative |
| 4 | **A vault value never appears in the answer, the trace or the log** | a token leaks, permanently |
| 5 | `authorization` in `headers` is refused, naming the header | the agent can bypass the vault |
| 6 | A non-GET redirect is reported, not followed | a POST silently becomes a GET and loses its body |
| 7 | A redirect to a private address is refused on the hop | the SSRF guard only checks the typed URL |
| 8 | A body over `LIMIT_BYTES` stops at the cap while reading | the phone OOMs on a hostile response |
| 9 | A `file://` or `ftp://` URL is refused | the scheme guard is bypassed |
| 10 | Two POSTs to one URL do not overwrite each other's file | the second answer points at the first's bytes |
| 11 | A missing secret is a refusal naming what would create it | the agent reads "401" and concludes the server is broken |

Test 4 belongs in `KeySafetyFeatureTest`, which already asserts the token never reaches a message.

## 2. What must be removed

### 2.1 `fetch` — subsumed, and deleted

`fetch` is `http` with `method: GET` and a fixed folder. Keeping both means two descriptions in the
cache prefix and two ways to say the same thing — the same defect the operator already fixed twice
(`create`/`edit` → `write`; `-u` flag → `archive`).

**Deleted:** the `KEYS` entry, the `specs()` entry, the `when` arm, `private fun fetch(...)`, the
`fetchAllowed()` plumbing **only if** nothing else reads it (checked below), and `Fetched.DIR`.

**Kept:** `Fetcher`, `Fetched.nameFor`, `Fetched.LIMIT_BYTES` — `http` uses all three.

**Before deleting, check:** `fetchAllowed` gates `fetch` at the dispatch table and is passed into
`specs()`. `http` must honour the same switch, so **`fetchAllowed` becomes `httpAllowed`** — a rename,
not a deletion, and the settings screen's label changes with it.

### 2.2 `gh` — never built

It was the obvious shape and it is the wrong one: a typed method per endpoint is what made
`CiSetup` take five compile rounds and what leaves four `REPOSITORY:` bindings to keep in step. `http`
covers it, and when GitHub adds an endpoint the app needs no change.

### 2.3 `ci`, `runs`, `artifact` — **kept, deliberately**

They are three thin wrappers over `runs`/`logs`/`artifacts`/`artifactBytes`, and `http` could replace
them. They stay because:

- **`runs` files the log and opens the seal** (§3c). `http` would return ciphertext and the agent would
  have to know about `MUFFY_LOG_KEY`, which is exactly the machinery the operator wants out of the
  agent's way.
- **`artifact` unseals and unpacks.** Same reason.
- **They are the common path.** Making the agent assemble `GET /actions/runs?head_sha=…` for the
  everyday question is more prompt text for no capability.

**The rule that keeps them honest:** they are *conveniences over `http`*, and any one that grows a
mechanism `http` cannot express is a candidate for deletion. They are already the shortest expression
of what they do.

### 2.4 `mcp` — **kept, and it cannot be removed**

Checked, not assumed: `Mcp.kt:332` performs **three** POSTs — `initialize`,
`notifications/initialized`, then `tools/call` — with `Mcp-Session-Id` echoed between them, accepting
`text/event-stream` answers. `http` is one request. Replacing it would make the model hand-assemble a
JSON-RPC session across three calls and remember a session id, which is more prompt than code and
breaks on the first SSE answer.

**`mcp` is a protocol, not a request.**

### 2.5 `browse`, `shot` — **kept, and they were never HTTP**

Both are backed by `WebViewBrowser` — Chromium, from the OS, no APK cost. `browse` runs JS, waits for a
condition, then extracts text; `shot` calls `drawToBitmap`. **There is no HTTP request that returns a
rendered page or a picture of one.** They look like HTTP wrappers from the tool list and they are not.

## 4. The size question, settled

Two limits, two jobs, and only one of them is new work:

| Limit | Protects | Where |
|---|---|---|
| `forConversation` (token budget) | the context | `AgentTools.kt:4361` — already applies to every tool |
| `LIMIT_BYTES` (100 MB) | the process | `Fetcher` — counted **while reading** |

**`forConversation` cannot replace `LIMIT_BYTES`**, and the reason is concrete: `fetch` writes bytes to
a file and never puts them in the conversation, so `forConversation` sees a sixty-character sentence and
never sees the 100 MB. A cap that fires after the phone has buffered two gigabytes is not a cap.

**`http` therefore adds no new limit.** It reuses both, in the places that already exist.

## 6. What this does *not* solve, stated plainly

- **A workflow cannot answer a question.** It starts only from a push or a dispatch, so "what branches
  exist" is `http`, not a workflow. Workflows are for *work*; `http` is for *asking*.
- **A workflow round trip costs a runner start** — 20.7 s of setup, measured. Right for something
  substantial, wrong for something `http` answers in 200 ms.
- **Secrets stay app-only.** `http` reads the vault; it cannot write one. A `PUT` to a secrets endpoint
  could overwrite the keystore and silently break releases, and nothing would report it.
- **Repo creation and deletion stay app-only.** A `DELETE /repos/…` has no undo.
- **This does not make the account fully agent-managed.** It makes the *API* reachable without new app
  code, which is the part that was blocking everything else.

## 7. The protocol boundary — what `http` can and cannot reach

**`http` is a request. `push` is a protocol.** They look like the same category from the tool list and
they are not, and the difference decides which tools survive.

| | `http` | `push` / `pull` |
|---|---|---|
| Shape | one request, one response | ref negotiation, then a packfile |
| State | none | the local tree, the LFS store, the locks |
| Auth | an `Authorization` header | JGit `CredentialsProvider`, plus LFS's own auth |
| App rules it honours | the address guard, the vault, the filing rule | *"commit first, so what is sent is a thing you can point at"*, LFS objects **before** refs (GitHub rejects a tree naming an absent object — GH008), `RepoLocks.hold` |
| Could `http` do it? | — | **No.** `POST /git-receive-pack` needs a packfile the app would have to build, and it would bypass every rule above. |

`push` and `pull` take **no arguments** (`setOf()`). There is nothing for the agent to point at: the app
resolves the repository, the remote, the token, the LFS objects and the refs. That is the correct split,
because *when* to push is a judgement and *how* to push is machinery that was debugged for weeks.

### What the agent's workflow loop actually looks like

"Use workflows as stdin and stdout" reads like one command. It is three, and that is fine:

```
write  {"path": ".github/workflows/build.yml", "text": "…"}   → commits
push                                                          → sends it
ci     {"workflow": "build.yml"}                              → dispatches
runs   {"run": 4218…}                                         → files the log, opens the seal
```

The workflow reads its input from the checkout (a file the agent wrote) and returns its output as a
sealed artifact, which `artifact` unseals. **The agent never learns about `MUFFY_LOG_KEY`** — that is
the whole point of `runs` and `artifact` being tools rather than `http` calls.

## 8. Provider config — the endpoint becomes a file

`Door.kt:845` hardcodes one endpoint and `Door.kt:522` pins three OpenRouter-only fields. The rest of the
body (`model`, `messages`, `tools`, `stream`) is universal, and the response reader expects the OpenAI
shape, which Groq, Together, DeepSeek-direct, Fireworks, vLLM and Ollama all speak.

**So a config file replaces exactly the provider-specific part:**

```json
{
  "endpoint": "https://api.deepseek.com/chat/completions",
  "headers": { "Authorization": "Bearer {{key}}" },
  "body": { "model": "{{model}}", "messages": "{{messages}}", "stream": true },
  "reads": { "content": "choices[0].delta.content",
             "tool_calls": "choices[0].delta.tool_calls" }
}
```

**What it buys:** any OpenAI-compatible endpoint, by editing one file. `provider.only` and
`allow_fallbacks` stop being Kotlin and become template fields — a deletion.

**What it cannot do, stated honestly:** Anthropic's Messages API and Google's `generateContent` are
*structurally* different — different message shapes, different tool-call format, different streaming
events. Those need a **response parser**, not a template. The config covers the ~90% that copied
OpenAI's shape.

**The cost that is easy to miss:** the assembled body is currently pinned by a Kotlin test — *"the
assembled body is the thing worth pinning rather than the call that wraps it"*. Moving it into a config
moves that guarantee from **compile time to runtime**, so the config must be **validated on load**, not
on first use. A typo has to be a refusal at the settings screen, not a mystery 400 during a turn.

## 9. Rejected: an embedded sequence/protocol runner (with the evidence)

The operator's question: *"can a protocol be just an HTTP sequence file that you can supply as an
argument to `http` and it will be executed automatically?"* The idea is sound and the tools exist. Both
were checked against their real POMs, and both are wrong **for this app** — not in general.

### 9.1 JetBrains HTTP Client (`ijhttp`) — disqualified by its dependencies

`http-client-lang`'s POM depends on:

```
com.jetbrains.intellij.platform : core          (runtime)
com.jetbrains.intellij.platform : analysis-impl
com.jetbrains.intellij.platform : core-impl
com.jetbrains.intellij.platform : util
```

That is **the IntelliJ platform**, not a library. There is no Android story for it.

### 9.2 Karate — disqualified by its strength

Karate got the hard part right: `karate-js` is a JavaScript engine written from scratch in Java, **zero
dependencies**, deliberately avoiding `javax.script` (absent on Android). But `karate-core` pulls in:

```
httpclient5 · netty-handler · netty-codec-http · snakeyaml · fastcsv
thymeleaf · picocli · json-path · json-smart · dec
```

- **`httpclient5` and Netty duplicate `Fetcher`**, which is already proven and already runs
  `Addresses.problem` on **every redirect hop**.
- **`picocli` is a CLI framework** for an app with no shell.
- **Karate's JS has Java interop** — its README: *"bridge Java and JS code; full control… introspection
  from Java"*. An LLM with a Java-interop JS engine inside the app that holds the vault is `Class.forName`
  → `Runtime.getRuntime().exec`. That is `sh`, with a worse surface.

**And the decisive one: Karate's HTTP client would bypass `Addresses.problem`.** The app's rule is *"the
address rule first, before anything is opened"*; a second HTTP client with no such check would quietly
retire it. That is a regression disguised as a feature.

### 9.3 What survives from the idea

**Not nothing.** `.http` files are a de facto standard, so an agent may already know how to write one.
That argues for a **very small, closed subset** of that shape — not a YAML DSL, and never a language
runtime:

- requests, in order, with named variables captured from earlier responses
- **no loops, no conditionals, no JavaScript** — a sequence that can loop is a program, and a program
  needs an interpreter, and an interpreter needs a sandbox this app does not have
- every step goes through `Fetcher.request`, so the address guard, the vault and the filing rule all
  apply unchanged

**Build it only after `http` has been used, and only with evidence of what the two-call pain actually
was.** A sequence runner that hides the middle step also hides which step failed.

### 9.4 Anti-finding: artifact upload is not the stdin

There is **no upload path in `GitHub.kt`** — `artifacts` and `artifactBytes` are both download-only. It
is tempting to add one so the agent can "post files to a workflow." **Don't.**

A file in the repo — written, committed by `write`, pushed — is visible to every job's checkout, is
versioned, and the agent already knows how. An artifact upload happens *after* the run starts, needs the
run id, goes to a different host (`pipelines.actions.githubusercontent.com`, not `api.github.com`), and
is invisible to the checkout.

**The stdin is a commit.** The only file-post `http` needs is a request body from a path:

```
http { "method": "PUT", "url": "…", "body": "@notes/data.json" }
```

`@path` reads the file and sends its bytes — ~5 lines, and it means the agent can post something it just
built without pushing it through the context.

## 11. Git as a command, and how far a remote config can go

The operator's question: *"is it possible to implement git same way as http, so that it is a single cli
command that agent can use? and can we add remote protocol config on top of it so that we can setup any
git compatible cloud provider, or workflows, artefacts, releases and other things we use are github
specific?"*

### 11.1 Git is already one command, and it must not become `http`

`push` and `pull` already take **no arguments** (`setOf()`). The agent says `push`; the app resolves the
repository, the remote, the token, the LFS objects and the refs.

**What makes that work is JGit speaking the protocol, not the app.** `GitService.push` calls
`git.push().setRemote("origin")`; JGit does the ref negotiation and builds the packfile. Reimplementing
that on `Fetcher` means writing a packfile builder and a `git-receive-pack` parser — and re-earning every
rule the app already enforces (the dirty check, LFS objects **before** refs, `RepoLocks`).

**The model is not "git is http".** It is:

| | `http` | `push` / `pull` |
|---|---|---|
| Shape | one request, one response | ref negotiation + packfile |
| State | none | the working tree, the LFS store, the locks |
| Who drives it | **the agent** | **the app** |
| The agent needs to know | the URL | only *when* — `state` answers that |

### 11.2 What is portable today, and the two things that block it

Of the 24 `GitHub` methods:

| Category | Methods | Portable? |
|---|---|---|
| Git protocol (JGit) | clone, fetch, push, pull | **Yes, already** — `setRemoteUrl` takes a string |
| Identity / repos | `identity`, `listRepos`, `createRepo`, `renameRepo`, `deleteRepo`, `cloneUrlFor`, `webUrl` | API-shaped; GitLab/Gitea have equivalents |
| Actions / CI | `runs`, `jobs`, `logs`, `artifacts`, `artifactBytes`, `dispatch` | **No** — GitLab Pipelines and Gitea Actions are different products |
| Secrets / environments | `environments`, `putEnvironmentSecret`, `environmentKey`, … | **No** — every provider differs |

**Two blockers, both small, one of them a live bug:**

```kotlin
// GitHub.kt:1179
const val API = "https://api.github.com"
```

```kotlin
// GitService.kt:366 — the clone
if (Secrets.isGitHubHost(remoteUrl)) {
    credentials(token)?.let { command.setCredentialsProvider(it) }
}
```

**The second one silently refuses to authenticate against any non-GitHub host.** The token never reaches
the request, so a GitLab clone of a private repo fails as though the credentials were wrong. The same
guard is at `GitHub.kt:683, 763, 1047, 1129`.

That guard was correct when GitHub was the only provider. It is now **a wall that fails silently**, which
is the one failure mode the app's rules forbid. Even without a config file, `isGitHubHost` should become
*"is this a host we have a token for"* rather than *"is this github.com"*.

### 11.3 What a remote config file would be worth — and its limit

A narrow config gets you **clone, push and pull against any HTTPS git host**, which is the genuinely
portable part:

```json
{
  "name": "gitlab",
  "cloneUrl": "https://gitlab.com/{owner}/{name}.git",
  "api": "https://gitlab.com/api/v4",
  "auth": { "header": "PRIVATE-TOKEN", "secret": "gitlab-token" }
}
```

**What it does not get you: workflows, artifacts, releases.** Those are not "GitHub-specific in a
configurable way" — they are different products. GitLab CI is `.gitlab-ci.yml`, a different trigger
model, a different artifact API. A config that pretended otherwise would be a fiction, and the agent
would write a workflow that silently never runs.

**So the layering is:**

```
remote config  →  the git host          (clone / push / pull)
http + auth:   →  everything above it   (pipelines, releases, any API)
```

`http` is the escape hatch, and it is the reason §1 exists. The config file buys the host; `http` buys
the rest.

### 11.4 Anti-finding: do not build a GitHub-shaped abstraction for non-GitHub providers

The tempting mistake is a `Ci` interface with `GitHubCi` and `GitLabCi` behind it. It looks like the same
abstraction and it is not: the *model* differs (workflow file vs `.gitlab-ci.yml`), the *trigger* differs
(dispatch vs pipeline variables), the *artifact* differs (sealed zip vs job artifacts API), and the
*secrets* differ completely.

An interface over those would either be so thin it saves nothing, or it would force GitLab into GitHub's
shape and lose what makes it usable. **The honest answer is that the app is GitHub-shaped above the git
layer, and `http` is how anything else is reached.**
