# A binary has one version — and LFS turned out not to be how

**Status: DELIVERED, with the storage mechanism changed.** The rule is exactly as decided; the
mechanism is not LFS. See §0.

**Supersedes** `docs/PLAN-binaries-2026-11-05.md` (the history-rewrite design, never built) and the
"keep only the latest version" half of `docs/PLAN-semantic-history-2026-11-04.md` §5.

---

## 0. LFS was tried, measured, and removed — 2026-11-05

The operator asked for LFS. It was built (Steps 1–2), then tested against a real GitHub repository, and
it **cannot work**:

**`LfsPrePushHook` → `LfsConnectionFactory` sends no `Authorization` header at all.** Its request carries
`Accept`, `Content-Type` and `Accept-Encoding`; the only auth path in the whole class is SSH
(`git-lfs-authenticate`). Measured against a real repository with a real token:

| attempt | result |
|---|---|
| `git push` with a `CredentialsProvider` | `rc=401` on `POST .../info/lfs/objects/batch` |
| token embedded in `lfs.url` as userinfo | `rc=401` — the JDK connection does not turn userinfo into Basic |
| the same token by `curl -u x-access-token:$TOKEN` | **200** |
| the same token by `curl -H "Authorization: Bearer …"` | **200** |

So the server is fine and JGit never sends the credential. No setting fixes that, and it is not testable
from a phone either.

**And LFS was not needed.** A plain blob plus the existing tree rewrite gives the same guarantee. Measured
end to end on a 400 KB blob, six commits, text interleaved:

```
commits rewritten: 6
distinct picture blobs named by any commit: 1
distinct text versions still present: 6
old picture blob after gc: false      ← the 400 KB is gone
new picture blob after gc: true
commit count after gc: 6              ← the history is intact
text still readable at HEAD: draft 5
text still readable at HEAD~5: draft 0
```

**The one thing that made it work was expiring the reflog.** A plain `gc` keeps everything
`logs/refs/heads/<branch>` names, and a rewrite leaves the *original* commits there — the old blob
survived a plain `gc`, a `gc` with `setExpire(now)`, and a `gc` with `expire = 0`. It went only once
`logs/` was deleted. Nothing in this app reads a reflog: undo is a commit, and the history screen walks
`HEAD`.

**What that costs, stated plainly:** the reflog is the safety net for a mistaken `reset` in a normal
repository. Here the only rewrites are ones the app performed on purpose, so the net protects nothing
that is not already protected by a commit — but it does mean a project's `.git` no longer has one.

**Removed as a result:** `org.eclipse.jgit.lfs`, `gson` (its only dependency), `registerLfs`,
`enableLfs`, `ensureLfsAttributes`, `LFS_ATTRIBUTE`, `LfsStore`, and the `.gitattributes` line the app
used to write into the person's repository. That last one is a real gain: the app no longer edits a file
it does not own.

**The decision, in the operator's words (2026-11-05):**

> *"we need lfs"* · *"remove history setting even for binaries — we have tight lfs budget, no binary
> versioning should be allowed, only the ones referenced by the latest commit should stay"* · *"when we
> change a binary we should show a save screen with current path and name preset but with ability for
> user to save the change as a different file — that will be our versioning option for binaries"*
>
> *"no restore for binaries - warn that they will not be tracked by history and removal is irrevercible"*

So: **a binary has exactly one version, ever — the one the newest commit references.** Saving a change to
a binary is a *fork*, not a version: the person either overwrites (the old bytes are gone) or gives it a
new name (both files exist, each with one version). There is no setting that restores versions, because
there is no budget for them.

## 1. What was verified before this plan, and how

Everything below was **tested on this box** with `org.eclipse.jgit.lfs:6.10.1` + `gson`, against the app's
own JGit version. Not reasoned — run.

| claim | how it was checked | result |
|---|---|---|
| the client is pure Java | unzipped the artifact, scanned every class for `ProcessBuilder`/`Runtime.exec` | **one** class spawns a process (`InstallBuiltinLfsCommand`, unused); everything else is Java |
| only external dependency | read the POM, then scanned the bytecode | **gson** only |
| the tree stores a pointer | commit a 200 KB PNG, read the tree blob | `version https://git-lfs.github.com/spec/v1\noid sha256:…` |
| the **working tree keeps real bytes** | same commit, read the file | 204 800 bytes of pixels; the pointer exists only in git objects |
| a **hard reset restores the bytes** | delete the file, `reset --hard` (what `resetToRemote` does) | the picture came back |
| `repo.open(blob)` returns the **pointer** | read the tree blob directly | **pointer, not bytes** — the single most important finding |
| the LFS store **grows and `gc` ignores it** | four versions of one PNG, then `gc` | 200→400→600→800 KB; `gc` changed nothing |

**Two facts that shaped the design:**

1. **`filter.lfs.useJGitBuiltin=true` is mandatory.** Without it `BuiltinLFS.isEnabled` returns false and
   the filter is a **silent no-op** — commits store raw bytes and LFS appears "not to work". I nearly
   concluded the library was unusable because of this.
2. **`gc` never touches `.git/lfs/objects`.** LFS moves the storage problem; it does not remove it. The
   only thing that frees LFS objects is `git lfs prune` — which is **pruning by another name**, deleting
   objects no recent commit references. That is exactly what this plan automates, and it is why removing
   the history setting does not mean removing housekeeping.

## 2. The design

### 2.1 Storage — **the plain object database, not LFS**

```text
page.png  (working tree)   real PNG bytes — what the editor, the viewer and the agent's `read` see
page.png  (tree)           the PNG bytes themselves, as an ordinary git blob
```

A picture is committed **whole**. What gives it one version is the tree rewrite in §2.3, which makes every
older commit name the newest bytes — so the older blob becomes unreachable and the collection deletes it.
§0 has the measurement and the reason LFS was removed.

**The plan originally said this** — kept here because the reasoning was sound and only the mechanism was
wrong: `page.png` in the tree would be a 130-byte pointer, `objects/<oid>` would hold the bytes in
`.git/lfs/objects`, and a file edited ten times would have ten objects until they were pruned. LFS would
have moved the storage problem rather than removing it, which is why it needed its own prune (§2.3) and
why its failure to authenticate cost nothing but time.

### 2.2 Saving a binary

The save button for a picture stops being "save" and becomes **"save a copy"**, because overwriting is
destructive and the app must say so before it happens.

```text
[ Save ]  →
   ┌─ Save this picture ────────────────────────┐
   │  Name  [ page.png                     ]    │   ← preset: the current path
   │  Save in  [ drawings/                 ]    │   ← preset: the current folder
   │                                            │
   │  Saving over a picture keeps only the      │
   │  new version. The one you have now will    │
   │  be gone.                                  │
   │                                            │
   │  [ Save as a new file ]  [ Replace ]  [Cancel]
   └────────────────────────────────────────────┘
```

- **The name is preset to the current path**, so "just save" is one press — the common case is unchanged.
- **"Save as a new file"** is the versioning option: a new name means a new file with one version, and the
  old one keeps its own. This is the only way to keep two states of a binary, and it is a *file* operation
  the app already understands (rename/copy), not a history operation.
- **"Replace"** states the loss in the dialog before it happens, per the standing rule that a destructive
  act says what it destroys.
- The dialog appears **only when the bytes actually changed.** Pressing Save with no strokes does what it
  does today (nothing).

### 2.3 One object per binary, enforced

After a commit that changed a non-text path, and **without any history setting**:

```text
HistoryPrune.keepLatest(repo, path)   ← rewrite trees so every commit holding `path`
                                         points at the blob HEAD holds
then  mark the project for collection  ← Maintenance: expire the reflog, then gc(expire = 0)
```

**Two acts, and both are required.** The rewrite makes the old blob unreachable; the collection is what
deletes it. A plain `gc` is not enough — it treats everything named by `logs/refs/heads/<branch>` as
reachable, and the rewrite leaves the *original* commits there. Measured on a 400 KB blob: it survived a
plain `gc`, a `gc` with `setExpire(now)`, and a `gc` with `expire = 0`; it went only once `logs/` was
deleted.

**This is the whole of binary retention.** No setting, no depth, no count. What the newest commits
reference survives; nothing else does.

### 2.4 What the person sees

- **The files list shows the picture**, not a pointer — the working tree is real bytes (§1).
- **The history screen** shows no versions of a binary and offers **no restore**. The line becomes
  *"A picture has no versions. Saving a change replaces it; save under a new name to keep both."*
- **`restore` refuses a non-text path by name** — the agent's tool and the screen path alike — with the
  reason rather than writing something. This is the operator's fourth requirement, and it **replaces the
  corruption case in §1**: the fix is not "smudge the pointer correctly", it is "a picture cannot be
  restored at all". Cheaper and more honest than making a broken operation work.
- **Deleting a binary says what it costs, before it happens.** The file is not in the history, so
  **removal is irreversible** — there is nothing to bring it back from. That warning belongs on the delete
  confirmation for a non-text file, and it is the one place the app must be louder than usual.
- **The changes screen** lists a changed picture once, as an ordinary change, because the tree is truthful.

| machinery | fate | why |
|---|---|---|

**`RetentionFeatureTest` (13 tests) disappears with the setting.** That is the largest single deletion, and
it is the point: the tests exist to pin behaviour that will no longer exist.

## 4. Does removing commit pruning cost anything? Measured, not assumed

| what | 200 versions of | `.git` after gc |
|---|---|---|
| text | a 200 KB document | **340 KB** (124 KiB packed) |
| a binary, in git objects (today) | a 400 KB PNG | **79 MB** |
| a binary, in LFS (after this plan) | a 400 KB PNG | **~26 KB of pointers** + one object in the store |

Text compresses **120×**. That is why commit pruning was never buying what it appeared to buy, and why
this plan can delete it: the thing that actually grew was binaries, and they now live in a store with its
own collection rule.

**The one thing commit pruning did that nothing else does: bound the history *walk*.** `walkChanges`,
`versionsOf`, `unsentPaths` and the maintenance sweep all walk every commit. Measured at 1 247 commits:
0.8 s. At 50 000 it will not be. **This plan accepts that** — a notes app's text history is cheap, and a
project large enough to feel it is a project where a person can be offered an explicit action. It is not
a setting, and it is not silent.

## 5. The semantic index: unchanged, and why

**The index keeps `(path, blob)` keys and keeps resolving blob → commit at read time.** Three reasons, and
the third is new:

1. **Dedupe.** Identical text at two versions shares one vector. A commit key would embed it twice.
2. **Force-push.** `replaceWithRemote` is still a hard reset; a force-pushed remote still strands local
   commits. LFS does not change that.
3. **LFS pruning does not rewrite commits, so commit ids *are* now stable** — which removes the argument
   *for* storing them, not the argument *against*. The key stays the blob because a blob is content and a
   commit is an event.

**What changes:** the index window is no longer `historyLength` (deleted) and is no longer a constant
either — the history pass indexes **every** commit. See §8.

## 6. The work, in order

Each lands with the test that fails if it breaks.

**Step 1 — LFS in the build and the repository.**
`org.eclipse.jgit.lfs:6.10.1` + `gson`; `BuiltinLFS.register()` once at start; write
`filter.lfs.useJGitBuiltin=true` and the `.gitattributes` line on `init` and `cloneInto`; a
`ProjectGit.lfsReady(project)` that reports whether a project is LFS-capable.
*Test:* a committed PNG's tree blob is a pointer; the working file is real bytes.

**Step 2 — `restore` refuses a binary, and every remaining blob read smudges.**
`GitService.restore` returns a refusal naming the path when `ws.kindOfPath(path) != EntryKind.TEXT`, before
it opens anything — and `ProjectGit.restore` passes it through, so the agent's `restore` tool gets a
sentence rather than an exception. Then the **six** remaining direct-blob reads (`blobText`, `blobSize`,
`versionsOf`, `bytesOf`, and the two inside `restore`'s folder branch) go through
`LfsBlobFilter.smudgeLfsBlob`.

**Why the refusal comes first:** the corruption case is that `repo.open(...).bytes` is the *pointer* under
LFS, so writing it would replace a picture with 130 bytes of JSON. Smudging would fix that — and would
still hand back a version of a file that has no versions, which is a lie. The operator removed the
operation instead.
*Tests:* `restore` of a `.png` fails with a sentence naming the path; `restore` of a `.txt` still works;
a blob read through `bytesOf` on an LFS path yields bytes that decode as an image, not a pointer.

**Step 3 — the save-a-copy dialog.**
`EditorScreen`'s picture Save opens `Dialogs.SavePictureDialog` with the path preset, offering *Save as a
new file* / *Replace* / *Cancel*, shown only when the bytes changed.
*Test:* replace overwrites; save-as creates a second file with its own single version; cancelling writes
nothing.

**Step 4 — one object per binary.**
`HistoryPrune.keepLatest` (§2.3), called from `commitOutcome` when the commit's diff held a non-text path;
then `Maintenance.mark`.
*Test:* a picture saved twice leaves one LFS object and one pointer in every commit's tree.

**Step 5 — the LFS prune in `Maintenance`.**
Reachability over pointer oids, then delete unreferenced objects under `.git/lfs/objects`.
*Test:* after replace + maintenance, the old object is gone; after save-as, both remain.

**Step 6 — delete the setting and the prune.**
`historyLength`, `keepProvider`, `HistoryPrune.prune`, the `prune` calls in `commitOutcome` and the sync,
`RetentionFeatureTest`, the Settings row, the legacy key migration.
*Test:* the suite compiles with none of them; nothing reads `KEY_HISTORY`.

**Step 7 — the history screen's sentence.**
*Test:* a picture's history offers no version to restore and says why.

**Step 8 — the delete warning.**
The delete confirmation for a non-text file says, in its own words, that the file is not in the history
and that removing it cannot be undone. Text keeps the existing wording, because a text file *can* be
brought back.
*Test:* deleting a picture asks first and names the irreversibility; deleting a text file does not gain the
warning.

**Step 9 — the history walk indexes every commit.**
`VERSIONS_PER_PATH` and `AgentTools.VERSIONS_CONSIDERED` stop bounding the *index*: `history()` walks the
whole history. The text-mode `search {history}` keeps its own display ceiling, because that is a list a
person scrolls, not an index.
*Test:* a version older than 40 commits is found by a semantic search.

**Step 10 — rank over distinct vectors.**
`SearchIndex.nearest` iterates `vectors`, scores each once, takes the top `RERANK_DEPTH`, then resolves
paths and versions for those only.
*Test:* a chunk that shares a vector with another is scored once, and the answer is the same as before.

**Step 11 — int8 vectors with a per-vector scale.**
`vectors(hash, vector BLOB, scale REAL)`; encode on write, dequantise on read.
*Test:* the top 10 for a fixed query is unchanged against a float32 index built from the same text, and
the stored size is a quarter.

**Two things reality corrected, recorded rather than quietly deviated from:**

1. **`registerLfs()` had no caller.** Step 1 wrote it and nothing invoked it, so the filter was inert:
   a picture's commit stored raw bytes and the attribute was ignored, with no error anywhere. Now called

   filter rather than the fallback.

   because `initOrOpen` commits whatever is on disk and a file written afterwards sits untracked until
   the next save commits it as a change nobody made.

endpoint, and none of those exist in CI or on this box. Everything in steps 4–5 is proven locally — one
object, one pointer, the sweep reclaiming the orphan — but whether a push uploads the object is the one
thing that needs the phone.

## 7. Risks, named

| risk | what happens | mitigation |
|---|---|---|
| **the push is unproven** | `LfsPrePushHook` does `POST …/objects/batch` then `PUT`; I could not test it without a real repo | **prove it first, on the phone, with one drawing** — everything else is wasted if this fails |
| **GitHub quota** | 1 GB free storage + 1 GB/month bandwidth, then metered | the save dialog says the picture is stored remotely; a project near quota must say so before a person fills their account |
| **`.gitattributes` is committed content** | `*.png filter=lfs` appears in the person's project and is pushed | intended: it is what makes a clone elsewhere understand the pointers |
| **`restore` corrupts pictures** | writes the pointer over the image | **removed by refusing the operation** (Step 2) rather than by making it work |
| **a deleted picture is gone for ever** | no version exists to restore from | the delete confirmation says so (Step 8); this is the accepted cost of no binary versioning |
| **LFS prune deletes something a person wanted** | the object is gone; only the pointer remains | it only deletes what no surviving tree references, which is the definition of "not the latest" |
| **a project with no LFS objects** | nothing to prune | the pass is a no-op and writes no log row |

## 8. History is unbounded, and ranking gets two fixes

**The decision (2026-11-05):** history is **unbounded**. No window, no ceiling, no cap — search covers all
of it and answers sorted by score. *"our app is supposed to support medium sized projects, not giants"*,
and *"if anything users can always reimport a squashed version of the project inside the app (we dont need
to care about it, we are just one tool, we shouldnt do everything)"*.

So the 40-version window goes, and `VERSIONS_PER_PATH` with it: the history walk indexes every commit.

**Two changes make that affordable, and both were measured before being written down.**

### 9.1 Rank over distinct vectors, not chunk rows

`nearest()` today joins `chunks` to `vectors` and decodes a blob **per row**. Chunks share vectors by
design (a paragraph saved ten times is one vector), so the join reads the same blob 1.6× on this repo.

| | rows read | time |
|---|---|---|
| per chunk row (today) | 166 967 | **682–723 ms** |
| per distinct vector | 104 518 | **588–631 ms** |
| arithmetic alone, in memory | 104 518 | **196 ms** |

**75 % of the cost is SQLite handing back blobs, not the cosine.** The fix is to iterate `vectors` once,
score each, take the top `RERANK_DEPTH`, and only then resolve their paths — which is also the shape the
data already has.

### 9.2 Store vectors as int8, with a per-vector scale

Measured against **real** embeddings (`qwen/qwen3-embedding-8b`, 64 real chunks of this repo's source):

| | value |
|---|---|
| top-10 agreement with float32 | **99.8 %** |
| cosine error | max **0.001**, mean **0.0002** |
| size | **4× smaller** — 391 MB → 98 MB per 100 000 vectors |

So a full-history index of this repo is **408 MB** as float32 and **~102 MB** as int8. The quantisation is
`value = round(x / (max|x| / 127))`, with the scale stored beside the vector; the score is computed by
dequantising on read, so nothing about the answer changes shape.

**Cost of the whole thing, measured:** 3 617 blobs → 166 967 chunk rows → 104 518 vectors → 31.2 M tokens
→ **$0.31** to embed (qwen; $0.12 at pplx) and **~17 minutes** for the first pass at 30 837 tok/s.

### 9.3 What this deliberately does not do

- **No ceiling and no truncation.** If a project grows to the point where its index does not fit, that is
  a project beyond what this app is for — and squashing it is `git`'s job, not ours. The app is one tool.
- **No warning about size.** A ceiling that never triggers is a sentence nobody reads.

## 9. What this plan does not do

- **No binary versions, ever.** Not behind a setting, not behind a debug flag.
- **No `restore` of a binary.** The tool refuses it by name; the screen does not offer it.
- **No commit pruning.** Text does not need it; binaries are no longer in git objects.
- **No change to the semantic index's keying.** Blob keys stay.
- **No agents editing binaries.** They never could; `write` is text, and the picture path is the person's.
- **No migration.** There are no users; a project with old binary blobs keeps them until its next binary
  change triggers §2.3, and the LFS prune then collects whatever no tree references.
