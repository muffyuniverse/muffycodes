# Binaries live in LFS, and a binary has no history

**Supersedes** `docs/PLAN-binaries-2026-11-05.md` (the history-rewrite design, never built) and the
"keep only the latest version" half of `docs/PLAN-semantic-history-2026-11-04.md` §5.

**The decision, in the operator's words (2026-11-05):**

> *"we need lfs"* · *"remove history setting even for binaries — we have tight lfs budget, no binary
> versioning should be allowed, only the ones referenced by the latest commit should stay"* · *"when we
> change a binary we should show a save screen with current path and name preset but with ability for
> user to save the change as a different file — that will be our versioning option for binaries"*

So: **a binary has exactly one version, ever — the one the newest commit references.** Saving a change to
a binary is a *fork*, not a version: the person either overwrites (the old bytes are gone) or gives it a
new name (both files exist, each with one version). There is no setting that restores versions, because
there is no budget for them.

---

## 1. What was verified before this plan, and how

Everything below was **tested on this box** with `org.eclipse.jgit.lfs:6.10.1` + `gson`, against the app's
own JGit version. Not reasoned — run.

| claim | how it was checked | result |
|---|---|---|
| the client is pure Java | unzipped the artifact, scanned every class for `ProcessBuilder`/`Runtime.exec` | **one** class spawns a process (`InstallBuiltinLfsCommand`, unused); everything else is Java |
| only external dependency | read the POM, then scanned the bytecode | **gson** only |
| the tree stores a pointer | commit a 200 KB PNG, read the tree blob | `version https://git-lfs.github.com/spec/v1\noid sha256:…` |
| the **working tree keeps real bytes** | same commit, read the file | 204 800 bytes of pixels; the pointer exists only in git objects |
| a **hard reset restores the bytes** | delete the file, `reset --hard` (what `resetToRemote` does) | the picture came back |
| `repo.open(blob)` returns the **pointer** | read the tree blob directly | **pointer, not bytes** — the single most important finding |
| the LFS store **grows and `gc` ignores it** | four versions of one PNG, then `gc` | 200→400→600→800 KB; `gc` changed nothing |

**Two facts that shaped the design:**

1. **`filter.lfs.useJGitBuiltin=true` is mandatory.** Without it `BuiltinLFS.isEnabled` returns false and
   the filter is a **silent no-op** — commits store raw bytes and LFS appears "not to work". I nearly
   concluded the library was unusable because of this.
2. **`gc` never touches `.git/lfs/objects`.** LFS moves the storage problem; it does not remove it. The
   only thing that frees LFS objects is `git lfs prune` — which is **pruning by another name**, deleting
   objects no recent commit references. That is exactly what this plan automates, and it is why removing
   the history setting does not mean removing housekeeping.

## 2. The design

### 2.1 Storage

```text
page.png  (working tree)   real PNG bytes — what the editor, the viewer and the agent's `read` see
page.png  (tree)           130-byte pointer: version, oid sha256, size
objects/<oid>              the bytes, content-addressed, in .git/lfs/objects
```

**One object per distinct content.** A file never edited has one object forever. A file edited ten times
has ten objects until they are pruned (§2.3).

### 2.2 Saving a binary

The save button for a picture stops being "save" and becomes **"save a copy"**, because overwriting is
destructive and the app must say so before it happens.

```text
[ Save ]  →
   ┌─ Save this picture ────────────────────────┐
   │  Name  [ page.png                     ]    │   ← preset: the current path
   │  Save in  [ drawings/                 ]    │   ← preset: the current folder
   │                                            │
   │  Saving over a picture keeps only the      │
   │  new version. The one you have now will    │
   │  be gone.                                  │
   │                                            │
   │  [ Save as a new file ]  [ Replace ]  [Cancel]
   └────────────────────────────────────────────┘
```

- **The name is preset to the current path**, so "just save" is one press — the common case is unchanged.
- **"Save as a new file"** is the versioning option: a new name means a new file with one version, and the
  old one keeps its own. This is the only way to keep two states of a binary, and it is a *file* operation
  the app already understands (rename/copy), not a history operation.
- **"Replace"** states the loss in the dialog before it happens, per the standing rule that a destructive
  act says what it destroys.
- The dialog appears **only when the bytes actually changed.** Pressing Save with no strokes does what it
  does today (nothing).

### 2.3 One object per binary, enforced

After a commit that changed a non-text path, and **without any history setting**:

```text
HistoryPrune.keepLatest(repo, path)   ← rewrite trees so every commit holding `path`
                                         points at the blob HEAD holds
then  mark the project for collection  ← Maintenance gc + LFS prune
```

This is the rewrite from the previous plan, and it is **still needed** — LFS does not make old objects
unreachable, because they are not reachable *by commits* in the first place. What changes is that it no
longer needs a setting, no longer needs a depth, and no longer needs to be bounded: a binary that changed
once is rewritten once.

**But it is not sufficient by itself.** `git gc` ignores `.git/lfs/objects`, so the collection must also
delete LFS objects that no surviving tree references. That is `git lfs prune`'s job, done by hand:

```text
reachable = every pointer oid in every tree of every commit reachable from HEAD
for each file under .git/lfs/objects:
    if its oid is not in reachable → delete
```

**This is the whole of binary retention.** No setting, no depth, no count. What the newest commits
reference survives; nothing else does.

### 2.4 What the person sees

- **The files list shows the picture**, not a pointer — the working tree is real bytes (§1).
- **The history screen** stops offering versions of a binary. The current line —
  *"This is not a text file, so a version of it cannot be read here. It can still be put back."* — becomes
  *"A picture has one version. Saving a change replaces it; save under a new name to keep both."*
- **The changes screen** lists a changed picture once, as an ordinary change, because the tree is truthful.

## 3. What is removed

| machinery | fate | why |
|---|---|---|
| **`historyLength` setting** (`SettingsStore`, `SettingsScreen`, `RetentionFeatureTest`) | **deleted** | no versions of anything to bound: text needs no bound (120× compression, measured), binaries have one |
| **`keepProvider`** (`ProjectGit`, `AgentWiring`, `AppViewModel` ×6, `ProjectGitTest`) | **deleted** | its only consumer was the prune |
| **commit pruning** (`HistoryPrune.prune`) | **deleted** | see §4 |
| **the prune trigger in `commitOutcome` / sync** | **deleted** | nothing to prune |
| the binary history rewrite as a *plan* | **kept, simplified** | §2.3 — no setting, no bound |
| `Maintenance` marker + `collect` | **kept, extended** | now also prunes the LFS store |
| **`search {history}` window = `historyLength`** | **replaced by a constant** | see §5 |

**`RetentionFeatureTest` (13 tests) disappears with the setting.** That is the largest single deletion, and
it is the point: the tests exist to pin behaviour that will no longer exist.

## 4. Does removing commit pruning cost anything? Measured, not assumed

| what | 200 versions of | `.git` after gc |
|---|---|---|
| text | a 200 KB document | **340 KB** (124 KiB packed) |
| a binary, in git objects (today) | a 400 KB PNG | **79 MB** |
| a binary, in LFS (after this plan) | a 400 KB PNG | **~26 KB of pointers** + one object in the store |

Text compresses **120×**. That is why commit pruning was never buying what it appeared to buy, and why
this plan can delete it: the thing that actually grew was binaries, and they now live in a store with its
own collection rule.

**The one thing commit pruning did that nothing else does: bound the history *walk*.** `walkChanges`,
`versionsOf`, `unsentPaths` and the maintenance sweep all walk every commit. Measured at 1 247 commits:
0.8 s. At 50 000 it will not be. **This plan accepts that** — a notes app's text history is cheap, and a
project large enough to feel it is a project where a person can be offered an explicit action. It is not
a setting, and it is not silent.

## 5. The semantic index: unchanged, and why

**The index keeps `(path, blob)` keys and keeps resolving blob → commit at read time.** Three reasons, and
the third is new:

1. **Dedupe.** Identical text at two versions shares one vector. A commit key would embed it twice.
2. **Force-push.** `replaceWithRemote` is still a hard reset; a force-pushed remote still strands local
   commits. LFS does not change that.
3. **LFS pruning does not rewrite commits, so commit ids *are* now stable** — which removes the argument
   *for* storing them, not the argument *against*. The key stays the blob because a blob is content and a
   commit is an event.

**What changes:** the index window is no longer `historyLength` (deleted). It becomes a constant —
`VERSIONS_CONSIDERED = 40`, which is what the text-mode history already uses, so both modes still agree.
The earlier objection stands and is answered in §8.

## 6. The work, in order

Each lands with the test that fails if it breaks.

**Step 1 — LFS in the build and the repository.**
`org.eclipse.jgit.lfs:6.10.1` + `gson`; `BuiltinLFS.register()` once at start; write
`filter.lfs.useJGitBuiltin=true` and the `.gitattributes` line on `init` and `cloneInto`; a
`ProjectGit.lfsReady(project)` that reports whether a project is LFS-capable.
*Test:* a committed PNG's tree blob is a pointer; the working file is real bytes.

**Step 2 — every blob read goes through the smudge.**
Nine call sites (`blobText`, `blobSize`, `versionsOf`, `bytesOf`, `restore` ×2, `walkChanges` consumers).
**`restore` is the data-corruption case**: today it writes `repo.open(...).bytes`, which under LFS is the
pointer text, so restoring a picture would replace it with 130 bytes of JSON.
*Test:* restoring an old picture gives bytes that decode as an image, not a pointer.

**Step 3 — the save-a-copy dialog.**
`EditorScreen`'s picture Save opens `Dialogs.SavePictureDialog` with the path preset, offering *Save as a
new file* / *Replace* / *Cancel*, shown only when the bytes changed.
*Test:* replace overwrites; save-as creates a second file with its own single version; cancelling writes
nothing.

**Step 4 — one object per binary.**
`HistoryPrune.keepLatest` (§2.3), called from `commitOutcome` when the commit's diff held a non-text path;
then `Maintenance.mark`.
*Test:* a picture saved twice leaves one LFS object and one pointer in every commit's tree.

**Step 5 — the LFS prune in `Maintenance`.**
Reachability over pointer oids, then delete unreferenced objects under `.git/lfs/objects`.
*Test:* after replace + maintenance, the old object is gone; after save-as, both remain.

**Step 6 — delete the setting and the prune.**
`historyLength`, `keepProvider`, `HistoryPrune.prune`, the `prune` calls in `commitOutcome` and the sync,
`RetentionFeatureTest`, the Settings row, the legacy key migration.
*Test:* the suite compiles with none of them; nothing reads `KEY_HISTORY`.

**Step 7 — the history screen's sentence.**
*Test:* a picture's history offers no version to restore and says why.

## 7. Risks, named

| risk | what happens | mitigation |
|---|---|---|
| **the push is unproven** | `LfsPrePushHook` does `POST …/objects/batch` then `PUT`; I could not test it without a real repo | **prove it first, on the phone, with one drawing** — everything else is wasted if this fails |
| **GitHub quota** | 1 GB free storage + 1 GB/month bandwidth, then metered | the save dialog says the picture is stored remotely; a project near quota must say so before a person fills their account |
| **`.gitattributes` is committed content** | `*.png filter=lfs` appears in the person's project and is pushed | intended: it is what makes a clone elsewhere understand the pointers |
| **`restore` corrupts pictures** | writes the pointer over the image | Step 2 — highest severity in this plan |
| **LFS prune deletes something a person wanted** | the object is gone; only the pointer remains | it only deletes what no surviving tree references, which is the definition of "not the latest" |
| **a project with no LFS objects** | nothing to prune | the pass is a no-op and writes no log row |

## 8. The one thing I still owe you

**The 40-version search window.** You objected — correctly — that inheriting 40 from a UI list was wrong,
and the fix was to tie it to `historyLength`. This plan deletes `historyLength`, so the window must come
from somewhere else.

I propose: **index every version the history holds** (which is now bounded by nothing), capped by a
measured **vector storage ceiling** (~150 MB per project), with the answer saying when it truncated. That
is the option you chose earlier ("index everything but warn when size exceeds 100 MB"), and removing the
setting makes it the only honest answer.

It is not built here because it is a separate change with its own cost, and this plan is already large.
**Say the word and it becomes Step 8.**

## 9. What this plan does not do

- **No binary versions, ever.** Not behind a setting, not behind a debug flag.
- **No commit pruning.** Text does not need it; binaries are no longer in git objects.
- **No change to the semantic index's keying.** Blob keys stay.
- **No agents editing binaries.** They never could; `write` is text, and the picture path is the person's.
- **No migration.** There are no users; a project with old binary blobs keeps them until its next binary
  change triggers §2.3, and the LFS prune then collects whatever no tree references.
