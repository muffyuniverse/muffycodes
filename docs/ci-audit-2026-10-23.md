# An external audit of this pipeline, and what came of it

On 2026-10-23 the whole pipeline — the workflow, all fifteen tools, the build
files, both documents, the scenario harness — was sent to
`moonshotai/kimi-k3.1-pro` through OpenRouter in **one request** with reasoning
effort set to `max`, and asked to audit it: the critical path with arithmetic,
every way the pipeline could report success having done nothing, the four caches,
the test selector, sharding, trust, and what was missing entirely.

This file exists so the next person knows what was asked, what it cost, what it
found, and — most importantly — which parts of it were confirmed and which were
not.

## What it cost

| | |
|---|---|
| input | **58,738** tokens |
| output | **67,122** tokens, of which **53,453** were reasoning |
| wall clock | **19m 8s** |
| cost | **$0.78** |

**It is expensive and it is worth it about once.** Nearly a dollar and twenty
minutes for a single answer is roughly twenty times a normal task in this project.
The value was concentrated: four genuine defects that neither the tests nor I had
found, in a workflow that had already been hardened twice. The value would not
repeat — a second audit of the same file would restate the first.

Where the money went is worth recording: the input was 58K tokens, so the cost is
dominated by **output**, and the output is mostly *reasoning* (53K of 67K). Asking
for less effort would have been cheaper and measurably worse: the arithmetic
(shard-count curves, the critical-path floor, the cache-hit reasoning) came out of
that thinking rather than from the prompt.

The transcript is not in the repository. The findings that mattered are here, and
the ones that did not are marked as such.

## What it found that was true

Four defects, each re-derived from the artifacts before anything was changed.

**A signed, installable APK could exist while a shard was still running.** The
"ask the suite" gate filtered out jobs with no conclusion and then asked whether
the *remaining* ones had passed — so shard 0 finishing first read as `green` while
shard 1 ran. With two shards that is the ordinary case. Reproduced with the same
`jq` on synthetic JSON, then fixed to a terminal wait that fails closed.

**`--base HEAD~1` answers the wrong question.** It is what the *last commit*
changed, not what the *push* changed. A push carrying an app commit and then a
documentation commit was classified documentation-only: no lint, no APK, green.
Fixed with `tools/push-base.sh` and `github.event.before`.

**A manual dispatch on any branch could publish a release.** The
`workflow_dispatch` clause bypassed the branch check, so a dispatch on
`development` would have published. Fixed: publication is `refs/heads/main` only,
and the tag is created with `--target "$GITHUB_SHA"`.

**Nothing verified that the tests that ran were the tests that were asked for.**
Every guard was about the *asking*. That is exactly the shape of the incident this
pipeline already had: a selector matching nothing, every shard idle, a green run.
Fixed with `tools/check-results.py`.

Alongside those: an empty selection was read as "nothing to do" (with two shards
that is a green run executing nothing); `ci` asked for `headSha` and never used it,
so it could report the previous commit's green; the scaling report had a branch
that could never run and compared summed worker-time with wall-clock budgets; three
source files were on no map line, so touching them silently widened every run to
the whole suite.

## Where it was wrong

Recorded because a plausible audit is more dangerous than an obviously wrong one:
the wrong parts read exactly like the right parts.

**"`actions: read` is missing, so the gate has been returning `unknown` forever."**
Not so. The logs show the query succeeded and printed the `running` branch. The
permission is fine. Acting on this would have added a permission and a comment that
were both untrue, while the real bug — the subset race — stayed in place.

**"The scenario suite runs on every pull request."** It runs when the selector
picks it, or when selection falls back to `ALL`. Not on every request.

**"Fixed-position sharding is no longer required by the cache."** This one is
*right and unapplied*: the selection now travels in an environment variable read at
execution time, so shard membership cannot perturb the configuration cache. The
code still deals by position; that is now a question rather than a belief.

## Where I was wrong

The audit said nine of ten scenarios had an empty `then` block, so their before
and after pictures were the same frame twice. True, and fixed — but for two of them
I then guessed the cause of the remaining identical pair and guessed wrong. I added
a `refreshChanges()` that made no difference, measured it, and reverted the commit
with a message saying so. **A wrong explanation attached to a harmless change is
worse than no change**, because the next person reads it as a finding.

## What the fix found on its own

`tools/check-release.py` was written to close an audit finding and immediately
found a defect the audit had not mentioned: the `scenarios.md` **asset** was copied
into the release unrewritten, so every picture link in the file somebody downloads
pointed at a folder that does not exist in a release. The release *body* was
rewritten; the asset was not. A link that works in one place and not another is
worse than no link, because nothing looks wrong until somebody clicks it.

That is the argument for checks over reviews, in one sentence.

## The price of a selector that can be wrong

The audit's sharpest disagreement was with `tools/test-map.txt`: a hand-maintained
table deciding which tests a pull request runs, with one unguarded failure mode —
a *valid but incomplete* line, where the source is known so there is no
full-suite fallback, yet the test that would have caught the breakage is absent.

The audit proposed deleting the narrowing entirely and running everything on every
non-document pull request, for about **+32s** measured (58s → 90s).

**Rejected, and the reason is the shape of the branches.** The map is used *only*
on pull requests. `main` and `development` run `changed-tests.sh --all`, which does
not read the map at all. So an incomplete line can only ever cause an incomplete
run before a merge — and `main` runs everything before anything ships. The risk is
a pull request that merges green and is then caught on `main`, which is the wrong
way round but is not a shipped defect.

Paid for instead with `tools/check-test-map.py` on every run: every test class
named, no stale names in either direction, every source accounted for or declared
always-full. It proves inventory, not coverage, and the tool says so in its own
docstring so nobody mistakes a green run for a proof.

If the map ever grows a failure that reaches `main`, this decision is the one to
revisit — not the map.

## What was considered and refused

**Merging delivery into the release build** (8–10s). Delivery must wait for tests
and lint, so folding it in would put the build behind both: a 3s start becomes a
70s one. Removing a job is worth ~45s; this would have cost ~60s.

**Building unsigned in parallel and signing only in `deliver`.** This is the good
version of that idea and it is still open. It removes the API gate, the subset
race and the signed-artifact-on-red path entirely, and it takes the signing key out
of the build's executable logic. It is deferred because it moves `apksigner` and
`zipalign` into the delivery job — a change to the release path, and the release
path is the one place in this pipeline that deserves its own run rather than a
ride along with something else.

## If this is ever asked again

- **Do not re-audit the same file twice.** The second answer restates the first.
- **Send the failures, not only the design.** The four real findings came from the
  section listing incidents that had already happened — the audit reasoned from
  *how this pipeline lies*, not from how pipelines generally lie.
- **Ask for the arithmetic.** "Where does the 58s go" produced the only honest
  statement about the floor (~53s) and the refusal to chase anything below the ±6s
  noise.
- **Verify every claim before acting.** Two of its confident claims were wrong, and
  one was right but unproven — a ratio that makes unchecked application worse than
  no audit at all.
